# Commercial positioning

**AEGIS is offline adversarial validation and hardening infrastructure for
fraud-model teams.**

It answers a question fraud teams cannot currently answer with their existing
tooling: *does hardening a detector against the fraud we have already seen
help against fraud we have not?* Everything below describes how that would be
used in a real institution. It is positioning, not a deployment claim — see
[Boundaries](#boundaries) for what this prototype is and is not.

---

## Where AEGIS sits

```
LIVE PAYMENT PATH                        (AEGIS is NOT here)
terminal -> acquirer -> network -> issuer -> authorization decision
        |
        | historical transaction logs + fraud labels   (batch, after the fact)
        v
AEGIS  (offline)
        - attack stress testing across the identified taxonomy
        - blind-spot analysis on what the detector actually missed
        - hard-positive generation from persisted escapes
        - LOAFO / generalization report
        |
        v
next model validation / retraining cycle
        (owned by fraud data-science and model-risk functions)
```

AEGIS consumes a batch export and emits datasets and a report. It never sees
a live authorization, never returns a decision, and has no path into the
authorization flow.

## Who uses it

| Team | What they get |
| --- | --- |
| **Fraud model validation / model risk** | An adversarial test a model must survive before promotion, and a generalization report that names where hardening did *not* transfer. This is the primary fit: these functions are already required to evidence that a model was challenged, and today have no accepted method for challenging it with attacks that do not exist yet. |
| **Fraud data science** | Reproducible hard-positive datasets drawn from real detector failures, plus the blind-spot analysis explaining which signals let them through. |
| **Security / financial-crime red teams** | Bounded, seeded, repeatable attack scenarios that can be re-run identically to compare two models or two release candidates. |
| **Issuer, acquirer and network fraud functions** | A common benchmark shape for asking "how does this detector behave against an attack family it was never trained on?" across models and vendors. |

## What it requires

* **Historical transaction data** — amounts, timestamps, transaction type,
  pseudonymous source/destination account identifiers, pre-transaction
  balances. Batch, not streaming.
* **Fraud labels** for that history.
* **Institution-specific feature mapping and governance** — the current
  21-column feature set is derived from PaySim's schema; a real deployment
  would map to the institution's own features and pass its own data-handling,
  privacy and model-governance review. That mapping work is not done here and
  is not trivial.

## What it outputs

* **Reproducible attack scenarios** — every corpus regenerates byte-identically
  from its seed, so a result can be re-checked rather than taken on trust.
* **Hard-positive datasets** — fraud that the detector actually missed,
  promoted with full provenance and validated for split overlap before it can
  enter a retrain.
* **Blind-spot evidence** — which transactions survived, at what risk scores,
  against which detector-visible signals.
* **A generalization benchmark** — LOAFO: hold one attack family out of
  hardening entirely, then measure recall on a fresh scenario of that family.

## Why this is worth doing offline

The expensive failure in fraud modelling is not a model that scores badly on
its test split; it is a model that scores well because it memorized the
attacks it was shown, and then meets one it was not. A static holdout cannot
distinguish those two cases. LOAFO can, and it does so without touching
production traffic, without a live integration, and without any change to the
authorization path.

In this repository that measurement returned **partial generalization**: two
of three families transferred, and one — mule-network structuring — caught 0
of 12 on its held-out fold. That is the product working. Finding the gap is
the deliverable.

## Boundaries

State these alongside any commercial description of AEGIS:

* **AEGIS is not in the authorization path.** It does not score live payments
  and has no code path that could.
* **The current prototype is not connected to live payment systems.** The
  deployed demo is a read-only surface over persisted benchmark artifacts.
* **PaySim is synthetic/reference data.** It is a public synthetic
  mobile-money simulator, not captured real transactions, and every attack in
  this repository is generated by AEGIS's own deterministic simulators. No
  real fraud cases are involved anywhere.
* **A real deployment would require institution-specific privacy, governance
  and integration controls.** Nothing here substitutes for that review.
* **No production-readiness claim.** See
  [`CLAIMS_AUDIT.md`](CLAIMS_AUDIT.md) for the full audit of what is and is
  not supported by the evidence in this repository.

No customer, pricing, partnership, regulatory approval, certification, or
data-protection guarantee is claimed or implied by this document.
